บทสรุป (Summary)

ส่วนนี้สรุปผลการประเมินประสิทธิภาพของระบบ USB Token Sign API จากการทดสอบแบบรอบด้านครอบคลุมการวัด Baseline, โหลดสภาวะปกติ (Load), การทดสอบสภาวะเค้นสูง (Stress), การทดสอบความเสถียรระยะยาว (Endurance), และการหาจุดแตกหักของระบบ (Breaking Point) เพื่อวางแผนรองรับปริมาณธุรกรรมอิเล็กทรอนิกส์ขององค์กรได้อย่างปลอดภัย

🛡️ 1. ขีดจำกัดสูงสุดของระบบ (Maximum Safe Capacity)

ระบบสามารถรองรับผู้ใช้งานพร้อมกัน (Concurrency) ได้สูงสุดที่ 44 ผู้ใช้งาน โดยยังคงรักษาอัตราความสำเร็จที่ 100% และให้ Throughput เฉลี่ยสูงสุดที่ 1.39 ไฟล์/วินาที แต่เวลารอของผู้ใช้แต่ละคนจะเพิ่มขึ้นสูงถึง ~26.89 วินาที (ช้าสุด 57.94 วินาที)

💥 2. จุดแตกหักของระบบ (Breaking Point)

เมื่อเพิ่มผู้ใช้งานพร้อมกันเป็น 46 ผู้ใช้งาน ระบบจะเริ่มเกิดข้อผิดพลาด Timeout Error ฝั่ง Client เนื่องจากคิวการรอฮาร์ดแวร์ยาวเกินกว่าระยะเวลารอของการเชื่อมต่อ โดยพบไฟล์ล้มเหลว 2 ใบจาก 92 ใบ (อัตราสำเร็จลดลงเหลือ 97.8%)

🔐 3. คอขวดหลักของระบบ (Hardware Queue Bottleneck)

กระบวนการที่ใช้เวลามากที่สุดคิดเป็นกว่า 80% ของเวลาทั้งหมดคือ USB Token Hardware RSA Signing เนื่องจากตัวฮาร์ดแวร์ USB Token ประมวลผลเซ็นดิจิทัลได้ทีละ 1 คำขอ (Single Hardware Queue) ส่งผลให้ Throughput รวมติดเพดานอยู่ที่ ~1.3-1.4 signs/sec ไม่ว่าจะเพิ่ม CPU/RAM มากเพียงใด

📄 4. ผลกระทบจากขนาดไฟล์ (File Size Impact)

ขนาดไฟล์ PDF ตั้งแต่ 200 KB ถึง 3 MB (1 หน้า ถึง 20 หน้า) ไม่มีผลกระทบอย่างมีนัยสำคัญ ต่อประสิทธิภาพโดยรวม เนื่องจากขั้นตอนการฝัง XML และสร้าง PDF/A-3B บน Server ใช้เวลาเพียง 1.8 - 22.6 ms เท่านั้น

💡 ข้อเสนอแนะเชิงสถาปัตยกรรม (Architectural Recommendations)

⏱️

1. Client Timeout Configuration

เนื่องจากระบบมีพฤติกรรมการเข้าคิว (Queueing) เมื่อมีโหลดสูงขึ้น ส่งผลให้ Round-Trip Time ของคำขอท้ายคิวอาจยาวนานถึงเกือบ 60 วินาที (จากผลที่ 44 Users เวลารอสูงสุด 57.94s)

👉 แนวทางแก้ไข: ตั้งค่า Timeout ฝั่ง Client Application ที่เรียกใช้ API นี้ให้ ไม่ต่ำกว่า 60 วินาที
🛠️

2. Hardware Scaling Strategy

การอัปเกรด CPU หรือ RAM ของ Application Server จะ ไม่ช่วยเพิ่ม Throughput ของระบบ เนื่องจากคอขวดอยู่ที่ฮาร์ดแวร์ USB Token ที่รองรับสูงสุด ~1.39 ไฟล์/วินาที

👉 แนวทางแก้ไข: หากต้องการเพิ่ม Speed ต้องใช้งาน Multiple USB Tokens (Load Balance) หรือเปลี่ยนไปใช้ Enterprise HSM
📥

3. Load Leveling via Message Queue

ป้องกันปัญหา HTTP Timeout เมื่อระบบถูกยิงคำขอเข้ามาพร้อมกันเกิน 40 คำขอ ซึ่งเสี่ยงต่อการเกิดความล้มเหลวในการส่งข้อมูล

👉 แนวทางแก้ไข: นำระบบ Message Queue (เช่น RabbitMQ หรือ Kafka) มาพัก Request ก่อนส่งให้ USB Token ประมวลผลตามคิว
